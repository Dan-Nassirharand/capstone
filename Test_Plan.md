### Out of scope

**Won't (Requirements part 7).** Nothing is built for these, so nothing is tested beyond the refusals noted:

- W-01 deletion without confirmation (only its absence is tested: TC-040, TC-046)
- W-02 model-based scoring (only its absence: TC-019)
- W-03 removing or editing a keep exception
- W-04 email or chat notices
- W-05 a web or graphical front end
- W-06 conventions not in the knowledge base
- W-07 recipes added after the cursor passed them
- W-08 parallel runs or instances (only the refusal: TC-035)
- W-09 commits to pull requests or recipe edits
- W-10 cycle time computed inside C1
- W-11 SmartHQ consumer and call center features

**Deferred Could items.**

- **REQ-04 (TC-004).** Dismissal uses GitHub's native resolve, with no code of ours. The case is written but not run, unless T11 has spare time.
- **NFR-09 at full scale.** A 20,000,000-recipe load is deferred because of seeding time and sandbox cost (CON-04). TC-022 runs at 2,000,000 recipes, and an Analysis extrapolates the result.

**Known limitations.** These are recorded as limits, not raised as defects:

- An abandoned run holds the active-run lock, and there is no cancel operation (spec 3.5).
- A deletion made outside C3 during an uncertain window is credited to the claimant (spec 3.8).
- NFR-02 is measured to when the label and comment are posted. GitHub's email or app delivery after that is not measured.
- The threshold of 70 and the penalties are examples until OQ-02. Tests use the fixed ruleset `test-v1` (part 5).
- Copilot output is not deterministic. Part 2 handles it with repeated trials.

**Third-party components not retested.** We test our configuration and our use of each, not its internals:

- GitHub event delivery, the pull request UI, and resolve
- The Copilot model
- API Gateway's SigV4 verification
- DynamoDB transaction, idempotency, and consistency guarantees
- AWS SDK retries
- picocli argument parsing
- The Terraform AWS provider

## 2. Verification and Validation Strategy

**Verification (the team, against the specification).** Every REQ and NFR except NFR-10 is verified by the team. Each check compares an output with the numbers in Requirements parts 5 and 6 and the interface contracts in spec part 3. The method is the one each requirement names: Test, Demonstration, Inspection, or Analysis. CON-01 to CON-04 are verified by Inspection. Verification is done when the M21 go/no-go test report is complete.

**Validation (pilot engineers and the Advisor, against stakeholder needs).**

- **NFR-10.** Five eligible pilot engineers run the observed first-time task (TC-023).
- **REQ-01 and REQ-02 (T11).** Each pull request author rates every C1 comment "useful" or "not useful". This asks whether citations help, not only whether they exist.
- **REQ-08 (T12).** A pilot engineer judges each flagged recipe they review as truly low quality or not. The GE technical liaison accepts the ruleset (OQ-02).
- **CON-05 and US-01.** The Advisor reviews the T11 and T12 results tables at M23 (TC-029) and makes the go or no-go decision at M21. Review cycle time comes from the organization's existing measurement (REQ-06, W-10).

**Test pyramid.**

| Layer       | Approx. count            | Where                                 | Coverage focus                                                                                                                                                                                | Part 4 cases                                 |
| ----------- | ------------------------ | ------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------- |
| Unit        | 120                      | Development; CI on every pull request | C4 rules, clamping, and the 69/70 boundary; request validation; claim and release branches with a mocked store; CLI parsing and exit codes; G3 range checks; G4 allowlist; C2 ranking and cap | None (counted in the CI report)              |
| Integration | 35                       | Development; CI on every pull request | DynamoDB transactions, worker fencing, replay cleanup, halt and resume, claim reconciliation, fault injection                                                                                 | TC-012, TC-016, TC-024, TC-038, TC-043, TC-048 |
| System      | 33 + 6 inspections       | Staging                               | End-to-end flows through API Gateway and the CLI, the sandbox repository, timing, security, and configuration inspections                                                                     | All other cases except those in the next row |
| Acceptance  | 3 cases + pilot sessions | Pilot                                 | First-time usability, usefulness, flag agreement, and Advisor sign-off                                                                                                                        | TC-004 (deferred), TC-023, TC-029            |

**Variables, metrics, tolerance, and trials.** C1 depends on a language model, so its outputs vary from run to run. C4 uses fixed rules, so its outputs do not.

| Item                  | Variables controlled                                                                                 | Metric                                                | Tolerance                                       | Trials                                   |
| --------------------- | ---------------------------------------------------------------------------------------------------- | ----------------------------------------------------- | ----------------------------------------------- | ---------------------------------------- |
| C2 retrieval (REQ-01) | Knowledge base tag `kb-fixture-v1`, `article_cap`, 20 seeded branches, Copilot model as chosen in T1 | Seeded pull requests whose mapped article is returned | 18 of 20 or more, in every trial                | 3 (60 pull requests)                     |
| C1 time (NFR-01)      | Same, plus diff size up to the review size limit                                                     | Seconds from triggering event to review               | 300 s or less for every pass; no tolerance band | 60 first passes, 10 pushes, 2 size cases |
| C4 scores (NFR-07)    | Ruleset `test-v1`, `recipes-seed-v1`                                                                 | Rows that differ between runs                         | 0                                               | 2 runs                                   |

A C1 case is never passed by re-running it until it passes. Every trial counts.

## 6. Pass and Fail Criteria

**Each test case.**

- **Pass:** every expected result in part 4 is observed exactly, at the threshold in part 3, and the evidence is recorded: command output, an API export, or a screenshot.
- **Fail:** any expected result is missing or outside its threshold, or any recipe is deleted that was not confirmed.
- **Blocked:** a precondition in part 5 is not available, such as AWS access or pilot engineers.
- **Not Run:** not yet attempted, or deferred.
- **Timed cases.** One measurement over its limit fails the case. Results are not averaged.
- **Model-dependent cases.** Every trial in part 2 counts toward the result.
- **After a fix.** The failed case and the other cases in its group are re-run.

**Defect severity.**

| Severity | Meaning                                                                                          | Effect on the plan                                                |
| -------- | ------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------- |
| Sev-1    | A recipe deleted without confirmation, an unattributed deletion, a security bypass, or data loss | Blocks every milestone until it is fixed and retested             |
| Sev-2    | A Must requirement fails its threshold                                                           | Blocks M21 and M23                                                |
| Sev-3    | A Should or Could requirement fails, or a validation target is missed                            | Allowed only with an Advisor waiver recorded in the results table |
| Sev-4    | A cosmetic or wording issue                                                                      | No effect                                                         |

**The plan as a whole.**

- **M21 go/no-go passes when:**
  - 100% of Must cases pass: the groups for REQ-01, REQ-02, REQ-07, REQ-08, REQ-09, REQ-10, REQ-13, NFR-01, and NFR-04.
  - TC-015 and TC-016 (NFR-02, NFR-03) pass.
  - 0 Sev-1 and 0 Sev-2 defects are open.
  - Any other result is a no-go, and the Advisor decides the retest date.
- **M23 pilot complete passes when:**
  - The M21 conditions still hold on the pilot stack.
  - 90% or more of the Should and Could cases that are not deferred pass, and each failure has a Sev-3 waiver.
  - TC-023 and TC-029 pass.
  - Every REQ and NFR has a recorded result.
- **The plan fails when:** any Must case fails at M23, any Sev-1 defect is open, or NFR-10 is "not verified" without the Advisor's acceptance.

## 8. Definition of Done

### A feature is done when

- [ ] Its unit and integration tests are written and pass in CI, and its part 4 cases are Pass with evidence linked.
- [ ] Each requirement it implements has its full case group passing, including the edge or failure case.
- [ ] Its pull request is approved by the other member (CON-02), with no unresolved review threads.
- [ ] The specification, the configuration keys, and the CLI `--help` text match the behavior. Any interface change is logged in the spec version log.
- [ ] No Sev-1 or Sev-2 defect is open against it. Each open Sev-3 defect has an Advisor waiver.
- [ ] It runs on staging from a clean `terraform apply`, and no test-only control is enabled in the pilot stack.
- [ ] The component owner signs off and the test lead records the result.

### The project is done when

- [ ] The M23 pass conditions in part 6 hold, and every REQ, NFR, and CON has a final status in the traceability matrix.
- [ ] TC-023 and TC-029 pass, or the Advisor has accepted a "not verified" result in writing.
- [ ] 0 Sev-1 and 0 Sev-2 defects are open. Every Sev-3 defect has a waiver and is listed as a known limitation.
- [ ] The README, the specification, this plan, and the setup and handoff notes are current, and all TC ID changes are logged.
- [ ] The final test report is in the M25 design report.
- [ ] Both members and the Advisor have signed off.
